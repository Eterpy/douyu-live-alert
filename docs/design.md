# 设计说明

本文说明服务如何判定开播与下播、如何避免误报和重复邮件，以及重启、断网、发信中断时的行为。日常使用只需阅读 [README](../README.md)。

## 架构

```
            ┌───────────── 每个房间一套 ─────────────┐
斗鱼弹幕 TCP/WSS ─► RSS 状态事件 ─┐                    │
(只用于唤醒)                       ├─► 采样调度 ─► betard HTTP 核实 ─► 状态机 ─► SQLite
默认 30 秒轮询 ────────────────────┘   (独立子进程，有总时限)     │ 会话/证据/邮件队列
            └────────────────────────────────────────┘
                                         邮件消费者 ─► SMTP 子进程（DATA 前复核资格）
```

- 一个进程同时监控 `DOUYU_ROOMS` 中的所有房间，每个房间有独立的状态机、采样循环和邮件消费者，共用一个 SQLite 数据库（按房间号区分）和单实例锁。
- 房间之间共享最多 4 个并发 HTTP 子进程名额，按优先级分配：确认窗口中**已到期、会被计入**的下一份样本最先，按“窗口必须重新开始”的截止时间早者优先；其次是实时事件和启动触发的检查，但每个房间每个轮询周期最多享受一次；其余（包括窗口内提前触发的样本）与定时轮询一起按先来先到排队。因此即使名额长期排满，或部分房间不断收到实时事件，等待第二份证据的房间最多只等一个请求的时长，其他房间的定时轮询也不会被饿死。排队时间不计入请求耗时，也不计入采样停滞看门狗。
- 发信在专用的 2 线程池中进行，不占用 asyncio 用于 DNS 解析的默认线程池；空闲的 SMTP 预连接全局最多 2 个，取不到名额时改为发信时再连接。预测为静默的确认（重启或证据中断后）不预连接。服务停止后，已排队的发信任务不会再开始新的发送尝试。
- 任一房间出现不可恢复的错误时，所有房间一起停止，进程退出交给 Docker 重启；各房间按下文的重启规则独立恢复。

服务使用 [aiodouyu](https://pypi.org/project/aiodouyu/) 的 `DanmakuClient` 接收 RSS 状态推送。HTTP 子进程读取有大小上限的 betard 响应，交给同一依赖的 betard 解析器。状态判定、场次持久化和发信去重由本项目实现。

## 状态判定

每次 HTTP 观察归入以下一种：

| betard 字段 | 判定 |
| --- | --- |
| `show_status=1, videoLoop=0` | `LIVE` 真人直播 |
| `show_status=1, videoLoop=1` | `REPLAY` 录像轮播，按非直播处理 |
| `show_status=2` | `OFFLINE` |
| 字段缺失或类型异常、房间号不符、超时、限流、解析失败 | `UNKNOWN`，不能用于任何确认 |

适配器除了使用库的归一化结果，还直接校验原始字段 `room_id`、`show_status`、`videoLoop`：库在缺少 `videoLoop` 时会给出 `is_live=True`，在缺少原始房间号时会回填请求的房间号，这两种情况在这里都记为 `UNKNOWN`。

RSS 事件只负责尽快唤醒 HTTP 核实，从不直接确认状态。HTTP 请求进行中收到方向相反的明确 RSS 时，丢弃这次响应并重新请求；方向相反的 RSS 还会清空确认窗口并暂停发信，直到新的 HTTP 结果到来。

默认的 TCP 弹幕连接是明文的。为防止错误或被注入的 RSS 持续压制提醒，每次 HTTP 结果都会核对自上次核对以来收到的全部 RSS 说法，而不只是最后一条：其中任何一条与 HTTP 相反即记一次否定（被它作废的响应同样计入），因此在一次请求期间先注入相反、再注入一致的说法也会被计数。连续 2 次被否定后，RSS 只用于唤醒检查，不再清空窗口、作废请求或暂停发信；直到某次核对时所有待核对的说法都与 HTTP 一致才恢复。由此，连续被作废的响应最多 2 份。

## 确认规则

| 场景 | 规则（默认值） |
| --- | --- |
| 首次启动 | 两份一致的有效观察，间隔至少 10 秒，建立基线。已在直播的场次全程静默。 |
| 开播 | 两次独立 HTTP 请求都判定为 `LIVE`，请求起始时间相隔至少 10 秒，且两份证据之间的间隔不超过 18 秒（10 秒间隔 + 8 秒 HTTP 超时）。中途出现非直播或 `UNKNOWN` 时重新计数；两份证据给出不同的可信开播时间时也重新计数。 |
| 下播 | 至少 3 份非直播观察，首尾跨度至少 120 秒，最后一份在确认时不超过 30 秒。可信的直播证据取消下播候选，带有轮播旧时间的直播读数按下节复核。HTTP 结果未知时清空候选，相邻非直播证据间隔超过 128 秒时重新计时。 |

可信开播时间指 betard 的 `show_time` 与库解析结果一致、为正整数，且不晚于本机时间 120 秒（容忍时钟偏差）。

### 轮播保护

betard 在轮播切换时可能短暂报告 `LIVE`，也可能在真人开播后继续沿用轮播的开播时间。最近一次 HTTP `REPLAY` 或被采信的 RSS 轮播事件启动 60 秒保护，由单调时钟计时。新的轮播证据刷新窗口。重启时按保存的 UTC 时间恢复剩余秒数，若本机时钟已回拨到该证据之前，则至多再观察 60 秒。

保护期内，尚未确认开播的房间会过滤开播时间缺失或不晚于轮播开始的 `LIVE` 读数。每份 HTTP 轮播证据只使用它自己的 `show_time`。字段缺失或收到 RSS 轮播提示时，以该次证据的接收时间作比较。已确认在播时，保护期内与已知轮播开始时间相同的读数仍记为 `UNKNOWN`/`replay_guard`，保留已有确认窗口。

满 60 秒后，即使开播时间相同，新的有效 `LIVE` 读数也会进入常规确认流程。默认仍需要两次相隔至少 10 秒的独立请求。沿用的轮播时间按未知处理。如果它与真实开播时间交替返回，服务仍可确认正在直播。重启重新收集样本，沿用停机补报规则。

下播候选期间，一份带轮播旧时间、已通过保护窗口检查的 `LIVE` 会暂停投递，并安排一次快速 HTTP 复核（默认 10 秒）。连续两份独立的此类读数可确认恢复直播。一份新的非直播读数会继续原下播窗口，只有实际非直播样本计入下播确认。HTTP 失败会清空候选。

本场已有可信开播时间时，轮播证据（包括没有开播时间的 RSS 轮播提示）可能让本场自己的开播时间落在轮播边界之前。保护期结束后，单份这样的读数仍按未知开播时间处理。连续的独立读数都给出本场开播时间，且首尾两份的请求相隔至少 `LIVE_CONFIRM_GAP_SECONDS`（默认 10 秒）时，恢复场次识别，例如在长停机重启后恢复下播提醒资格。相邻两份读数的间隔不得超过两个轮询周期加一次超时（默认 68 秒），因此确认间隔设得更长时，中间的常规轮询会维持连续性。下播候选期间被暂缓的复核读数和常规直播读数计入同一组连续读数，退出下播候选后继续累计；两次复核确认的是恢复直播，场次识别仍按上述规则单独判断。期间出现非直播、未知、其他开播时间、新的轮播证据或采信的 RSS 轮播/下播提示，都需要重新收集；RSS 开播提示与这些读数一致，不会打断累计。平台更正开播时间时，按同样的规则判断两次读数是否一致。

沿用轮播时间开播后，平台给出一个更晚的时间，可能是对本场的更正。若它不晚于本场确认时刻加 120 秒，且期间没有新的轮播或断流证据，服务按本场处理。在这个时钟偏差范围内，缺少独立证据的快速换场可能被合并。连续监控期间，两次独立读数给出一致的更正后，服务用它判断后续换场。若平台持续将录像标为真人直播，现有 HTTP 字段仍可能满足开播条件。

### 场次归属

- **续播**：本场已出现离线证据，并在首份离线证据后不超过 158 秒（下播窗口 + 轮询间隔 + HTTP 超时）以更晚的开播时间恢复直播，视为同一场续播：更新场次开播时间，不发新的开播邮件。服务持久化“最后一份能确认属于本场的读数”：只有已采信、不构成换场的直播读数，并且与上一份本场证据间隔不超过 158 秒，或带着本场的可信开播时间时，才会更新它。轮播读数（即使沿用本场开播时间）、离线读数、被轮播保护拦下的读数和新场次的读数都不更新。从没有这项记录的旧版本升级时，优先使用旧版本保存的中断前证据（而非最后一次有效读数，它可能已属于新场次），并按同样的规则校正旧版本记下的续播起点。首份离线证据与它的间隔超过两个轮询周期加一次超时（默认 68 秒）时，例如长停机后重启，本场可能在中断期间任何时刻已经下播，158 秒改为从这份本场证据起算。停机期间开播的新场次因此按换场处理，无论重启后先读到离线还是先读到新场次。长停机后，没有可信开播时间的场次无法再被确认是同一场，之后带新开播时间的短暂断流按换场处理：宁可多发一封开播邮件，也不漏发。
- **换场**：没有离线证据，或证据中断超过上述时限，而连续两份证据给出一致且更晚的开播时间时，归档旧场（下播邮件记为 `SUPPRESSED_SESSION_CHANGE`，因为旧场结束时间未知），新场正常发送开播与下播邮件。
- 首份离线证据的时间会持久化，断流期间重启后仍按续播规则判断。
- 下播邮件优先取本场最初的可信平台开播时间到下播确认窗口首份非直播观察之间的时长。若确认开播时缺少可信的平台时间，则取本场两封邮件正文中的确认时间之差（开播时间读取开播邮件正文中实际显示的值，兼容早期版本的格式与取整），按显示的整秒计算，再取整到分钟。静默场次（首次启动时已在播，或停机、证据中断期间开播且不符合补报条件）和恢复保护场次的确认开播时间晚于实际开播，不能用来计算，缺少可信平台时间时时长保留为未知。算出的时长为负时（直播期间主机时钟回拨，或平台时钟领先），时长同样保留为未知，HTML 邮件注明“时间记录异常，无法计算”。
- `status` 中开播邮件的投递延迟以本场最初的可信平台开播时间为起点。缺少这个时间时，投递延迟显示为未知。

## 重启与故障

| 情况 | 行为 |
| --- | --- |
| 重启时处于直播中 | 保留原场次，重新建立确认窗口。停机不超过 600 秒且满足配对规则时，正常发送下播邮件。 |
| 长停机后才发现已下播 | 关闭旧场次，下播邮件记为 `EXPIRED`。若重启后仍在直播且开播时间与原场次一致，恢复该场下播提醒资格。 |
| 停机或证据中断期间开播 | 重启后，或确认窗口开始前超过两个轮询周期加一次超时（默认 68 秒）没有成功的 HTTP 读取时（包括网络故障和直播中停机后换场）：两份一致的可信开播时间严格晚于中断前最后一份证据（同一秒视为无法区分）、且距今不超过 `STARTUP_MISSED_EVENT_WINDOW_SECONDS` 时照常提醒，否则静默。 |
| 从备份恢复后 | 平台开播时间未知，或不晚于恢复时刻加 120 秒时，场次受恢复保护（`SUPPRESSED_RESTORE`）。这 120 秒覆盖平台时钟可能的领先量。房间连续一个下播确认窗口（默认 120 秒）处于非直播状态后解除保护。 |
| HTTP 失败 | 记为 `UNKNOWN`，指数退避（5 秒起，最长 300 秒）；HTTP 429 至少等待 60 秒且不短于一个轮询周期。网络故障不会被当作下播。 |
| RSS 断线 | 不影响 HTTP 证据和确认；超过 10 分钟没有有效 HTTP 或 RSS 持续断开时，健康状态变为 `DEGRADED`。 |
| 采样停滞 | 采样协程长时间没有进展时抛错退出。 |
| 事件循环卡死 | 独立线程监视心跳，超过 120 秒未更新时以退出码 1 结束进程。Compose 不会因健康检查失败重启容器，因此需要进程自行退出。 |

## 邮件投递

- 邮件为 `multipart/alternative`，同时包含纯文本和 HTML 两个版本。HTML 只用表格布局和行内样式，不引用外部图片或字体，字体使用各平台自带的中文字体；不支持渐变的客户端显示同色系纯色。直播标题、主播名和发件人名称写入 HTML 前会转义。HTML 与纯文本一起在确认时写入邮件记录；升级前已在队列中的邮件只有纯文本版本。
- 每个场次、每种事件、每位收件人只有一条邮件记录（数据库唯一约束），重复的 RSS 和观察不会产生重复邮件。
- 默认只有同场开播邮件已被 SMTP 接受，才发送下播邮件；开播邮件仍在发送时，下播邮件等待（`WAITING_FOR_LIVE_EMAIL`）。
- 队列中的邮件只发给当前配置的收件人；更换 `SMTP_TO_ADDRESS` 后，发给旧地址的待发邮件记为 `SUPPRESSED_RECIPIENT_CHANGED`。
- 每封邮件带 `Date` 与 `Message-ID`；同一通知的重试使用相同的 `Message-ID`，便于收件方去重。
- 出队和发送正文前都会复核最新证据：已结束场次的开播信、已确认恢复直播（新场次）后的下播信会过期；证据暂时未知、过旧或方向不符（例如下播信遇到一次直播样本）时暂缓，不消耗重试次数。队列默认 900 秒过期。
- 主机时钟回拨、使邮件创建时间晚于当前时间时，邮件暂缓投递，不计重试次数；时钟追上后重新复核证据再发送。回拨超过 `MAX_NOTIFICATION_AGE_SECONDS` 时邮件过期，避免实际延迟超过该时限的两倍。证据是否新鲜同时按系统时钟和单调时钟计算，取较大的年龄：系统时钟回拨不会让旧证据显得新鲜，即使回拨幅度不足以让当前时间早于证据时间。服务刚启动、尚无读数时只用系统时钟，此时发信本来就要先等到新的有效读数。
- SMTP 在独立子进程中运行，总时限默认 45 秒。服务器对 `DATA` 返回 354 后，父进程复核资格并先持久化 `SUBMITTING`，子进程收到授权后才写入正文。授权前的失败可以重试；授权后超时、崩溃或回执丢失记为 `UNCERTAIN`，不再自动重发，避免重复邮件。
- 有效开播候选出现时可提前完成 SMTP 连接、TLS 和认证（`SMTP_PRECONNECT`），与 10 秒确认间隔重叠以降低延迟；预连接本身从不提交邮件。

### 邮件状态

| 状态 | 含义 |
| --- | --- |
| `SIMULATED` | dry-run 模式下的模拟记录 |
| `PENDING` / `RETRYING` | 等待发送 / 等待重试 |
| `PREPARING` / `SUBMITTING` | 正在发送（未授权正文 / 已授权正文） |
| `SENT` | SMTP 服务器已接受 |
| `UNCERTAIN` | 正文可能已提交但没有收到回执，不自动重发 |
| `FAILED` | 永久失败或达到最大尝试次数 |
| `EXPIRED` | 超过有效期或已过时 |
| `WAITING_FOR_LIVE_EMAIL` | 下播邮件等待同场开播邮件结果 |
| `SUPPRESSED_BASELINE` | 首次启动时已在播，或停机/证据中断期间开播且超出补报条件的静默场次 |
| `SUPPRESSED_NO_LIVE_NOTICE` | 同场开播邮件未成功发送，按配对规则抑制 |
| `SUPPRESSED_DISABLED` | 对应通知已关闭 |
| `SUPPRESSED_RESTORE` | 快照中尚未结束的场次，或恢复保护期间无法根据平台开播时间确定是在恢复之后开始的场次 |
| `SUPPRESSED_SESSION_CHANGE` | 换场时旧场结束时间未知 |
| `SUPPRESSED_RECIPIENT_CHANGED` | 收件人已更换，不再发给旧地址 |

## 数据

SQLite 数据库位于 `DATA_DIR/live_alert.db`（WAL 模式），包含：

- `monitor`：每个房间的确认状态、当前场次、最近证据时间、心跳与健康状态；
- `observations`：每次 HTTP 观察（默认保留 30 天）；
- `sessions`：直播场次；
- `outbox`：邮件队列；
- `delivery_attempts`：每次 SMTP 尝试的时间点。

新版本启动时自动迁移数据库结构，已有记录保持不变。

## 输入防护

- 房间查询和靓号解析共用 HTTP 子进程。每份响应正文上限 1 MiB，超限记为 `ResponseTooLarge`，重定向正文直接关闭。父进程校验子进程输出，超过 64 KiB 或格式异常记为 `WorkerProtocolError`。
- HTTP 与 SMTP 子进程以 `python -P` 启动，不把工作目录加入模块搜索路径，工作目录中的同名文件无法替换标准库或本项目模块。
- 标题和主播名去掉控制字符与无法存储的 Unicode 字符（含双向文本控制符）后再写入数据库和邮件；配置值必须是有效 UTF-8。
- 命令行进程的 umask 为 `077`。服务启动时先收紧已有数据库、WAL、共享内存和回滚日志的权限，再打开数据库。数据库文件及这些附属文件须为普通文件。

## 已知边界

- betard 和弹幕协议都是斗鱼的非官方接口，字段和行为可能变化。
- 最后一次资格复核之后，平台状态仍可能立即变化。
- 系统无法同时保证“绝不重复”和“绝不漏发”：回执丢失时选择不重发（`UNCERTAIN`）。
- 不足下播确认窗口的短暂断流会合并为同一场。
